# In-app updates (design, 2026-11-16)

The user, 2026-11-16: "I want an update system where I can click update inside the app, with a
notification saying 'New version of the app is available.'" Until 0.5.4 every Mac was updated by
hand: the DMG, or a tar over SSH to the second Mac. Ships in 0.5.5.

## 1. Decisions

- **Sparkle 2** (2.10.1, the latest stable on 2026-11-16), as SwiftPM's binary XCFramework
  (`app/Package.swift`). EdDSA-signed updates, the DMG served from GitHub Releases.
- **Self-signed, not sandboxed, not notarized.** Sparkle accepts an update when EITHER its EdDSA
  signature verifies with the installed app's `SUPublicEDKey`, OR its code signature satisfies the
  installed app's designated requirement (`SUUpdateValidator`, read 2026-11-16). Kleoth's DR is
  `identifier "dev.kleoth.app" and certificate leaf = H"6d1f…"` ("Kleoth Self-Signed"), so a
  `make-app.sh` build passes both, and TCC grants (bound to the same DR) survive the update.
- **Every nested piece is signed with the app's identity, inside-out** (`app/codesign-app.sh`:
  Installer.xpc, Downloader.xpc with its entitlements kept, Autoupdate, Updater.app, the framework,
  the app), never `--deep`. The XPC services are unused (no sandbox) but ship inside the framework.
- **The feed is a release asset**: `https://github.com/ofcRS/kleoth/releases/latest/download/appcast.xml`
  (`SUFeedURL`). Rejected: `appcast.xml` committed on `main` (raw.githubusercontent.com). Why:
  - one `gh release create` publishes the DMG and the feed that points at it together; a feed on
    `main` would be live (after a merge, behind a ~5 min CDN cache) before or after its DMG exists;
  - nothing to commit after the tag, and no PR just to publish a feed;
  - `latest` moves only with a published, non-prerelease release, so drafts and pre-releases never
    reach users.

  Cost: a release without `appcast.xml` makes the URL 404 and hides every later update. The release
  gate refuses that (§3). Each release's feed carries the previous items (fetched from the live
  URL), so "Version History" and skipped versions keep working.
- **Asks before installing.** `SUEnableAutomaticChecks` = YES (daily, `SUScheduledCheckInterval`
  86400, no Sparkle permission prompt), `SUAllowsAutomaticUpdates` = NO (no silent installs, no
  "install automatically" checkbox). Settings → General turns the daily check off.
- **No feed override in the app.** The e2e test points Sparkle at a local feed from a separate probe
  (`updatecheck`, §5), so the app has no defaults key or argument that changes its feed. It clears
  Sparkle's legacy `SUFeedURL` defaults override at start (`clearFeedURLFromUserDefaults`).

## 2. The app (`UpdaterController`, `UpdatePolicy`)

- `app/Sources/KleothApp/Updates/UpdaterController.swift` wraps `SPUStandardUpdaterController`
  (Sparkle's own windows) and is its updater delegate and user-driver delegate. Created by
  `KleothApp` or `AppDelegate` (whichever asks first), started in `applicationDidFinishLaunching`.
- **Gentle reminders** (Sparkle's API for background apps: a menu-bar app's alert otherwise opens
  behind other apps). `UpdatePolicy.sparkleShowsScheduledUpdate` (KleothCore, tested): Sparkle's alert
  shows a scheduled find only in immediate focus (for a menu-bar app: within ~3 s of start), with
  nothing in flight and no first-run window up. Every other find becomes the popover notice
  "New version of Kleoth is available" (Kleoth X · you have Y) with **Update**, which brings
  Sparkle's alert forward (release notes, Install Update). The notice goes when the user looks at
  the alert or the session ends.
- **Never over work in flight.** `UpdatePolicy.Activity`: a meeting recording, a meeting
  finalizing/transcribing/summarizing (`isProcessing`, set in the same main-actor turn the
  recording stops), a screen recording (`isActive`), a dictation (`isSessionActive`, or a pending
  row being retried). Sparkle's `shouldPostponeRelaunchForUpdate` holds the relaunch while any is
  true; a 1 s timer lets it go after two idle ticks; the popover says "Kleoth X installs after the
  meeting recording, then reopens." Sparkle's non-closable "Ready to Install" window is ordered out
  meanwhile. Sparkle asks to postpone only once per session, so `updaterShouldRelaunchApplication`
  refuses (= calls the install off) a second Install while still busy.
- **Activation.** Before Sparkle shows a window (a check the user asked for, or the launch alert)
  Kleoth becomes a regular app (`AppActivation.windowOpened`: Dock icon, ⌘-Tab, in front); at the
  session's end `windowClosed` drops it back unless History or Settings is open.
- **UI.** Popover: the notice (or the "installs after …" line) with the other notices, and a quiet
  "Kleoth 0.5.5 · Check for Updates…" row above the footer. Settings → General → Updates: Version
  "0.5.5 (10)", "Check for updates automatically", Check for Updates…. The app menu (present while
  History or Settings makes Kleoth regular): "Check for Updates…" under About.
- **Demo mode** (`-KleothDemo`: the smoke test, the films): `UpdaterController` never creates
  Sparkle's updater. No check, no network, nothing in defaults. Settings draws the row, inert. A demo
  launch has no `AppDelegate`, so `start()` is never called either.
- **`-KleothSimulateFirstRun`** reads onboarding as pending, so a scheduled find goes to the popover,
  never an alert over the welcome window. Sparkle's own "check automatically?" prompt never shows
  (`SUEnableAutomaticChecks` is in Info.plist).
- Sparkle's state lives in `dev.kleoth.app` defaults (`SULastCheckTime`, `SUHasLaunchedBefore`,
  `SUSkippedVersion`, `SUEnableAutomaticChecks` once toggled) and its downloads in
  `~/Library/Caches/dev.kleoth.app/org.sparkle-project.Sparkle/`.

## 3. The feed (`app/make-appcast.ts`) and the release gate

`bun app/make-appcast.ts` (docs/RELEASING.md step 9), after the final `make-dmg.sh`:
mounts the DMG read-only, reads its Kleoth.app (version, build, `LSMinimumSystemVersion`,
`SUFeedURL`, `SUPublicEDKey`) and runs `codesign --verify --deep --strict` on it; signs the DMG with
Sparkle's `sign_update` (the login Keychain key); writes `app/dist/appcast.xml` with the new item first
(title, pubDate, `sparkle:version` = CFBundleVersion, `sparkle:shortVersionString`,
`sparkle:minimumSystemVersion` 14.4, the CHANGELOG section as HTML in `<description>`,
`fullReleaseNotesLink` = CHANGELOG.md, the enclosure = the release DMG URL with `length` and
`sparkle:edSignature`), then up to 9 published items. It refuses, writing nothing, when:

| Refusal | Why it matters |
|---|---|
| the DMG's app ≠ `app/bundle/Info.plist` (version or build) | a stale DMG |
| the app fails `codesign --verify --deep --strict`, or has no Sparkle.framework | an update that can't be validated or can't update again |
| `SUFeedURL` ≠ the latest/download URL, no `SUPublicEDKey`, minimum macOS ≠ 14.4 | the next update would be unreachable or refused |
| CFBundleVersion not a plain integer, or not above every published build and the newest `v*` tag's | Sparkle offers only a newer `sparkle:version` (`9 < 10`, checked with Sparkle's own comparator by `updatecheck --compare`) |
| no CHANGELOG `## [<version>]` section | an alert with no notes |
| `sign_update` fails or prints no signature/length; the length ≠ the DMG's size | a feed every client rejects |
| the signature does not verify (Ed25519, in the script) against the `SUPublicEDKey` inside the DMG | the Keychain key isn't the app's key: every installed Kleoth would reject it |
| the output is not well-formed (`xmllint`) | |

The release gate (`marketing/sync.ts`, the `.claude/settings.json` hook on `git tag v…` /
`gh release create`) now also requires, for `check --release`, an `app/dist/appcast.xml` whose newest
item is this version's DMG at its release URL, with that DMG's length and a signature that verifies
against Info.plist's key (a DMG rebuilt after the feed fails it); and it blocks a non-draft
`gh release create` whose files leave out `appcast.xml`.

## 4. The key

- Generated 2026-11-16 with Sparkle's `generate_keys` on the build Mac. **Private key**: the login
  Keychain (`~/Library/Keychains/login.keychain-db`), a generic password, service
  `https://sparkle-project.org`, account `ed25519`, label "Private key for signing Sparkle updates".
  **Public key** (`SUPublicEDKey` in `app/bundle/Info.plist`): `yTDbk+ou+S2tX0bHQon6IL6hEZxmjH3eKtPZJAViTjA=`.
- Never printed, exported into the repo, or committed. `generate_keys -p` prints the public half.
- **Back it up** once, off the repo: `app/.build/artifacts/sparkle/Sparkle/bin/generate_keys -x <file>`
  writes the private key; store it in a password manager and delete the file. Another Mac:
  `generate_keys -f <file>`.
- `sign_update` reading the key asks for Keychain access the first time (a macOS prompt): Always
  Allow. Sparkle's tools are ad hoc signed, so a new Sparkle version's tool asks again.
- **Lost key.** Updates keep working only while the code-signing path holds: an app signed with the
  same "Kleoth Self-Signed" certificate is accepted on its code signature, and its new
  `SUPublicEDKey` must verify the archive (Sparkle's rotation rule). Lose both the key and the
  certificate (`~/Library/Keychains/kleoth-codesign.keychain-db`) and every install needs one manual
  reinstall. Back up both.
- **Developer ID later** (RELEASING.md §6): a Developer ID app no longer satisfies the self-signed
  DR, so that first release reaches existing installs through the EdDSA signature alone (same key),
  and TCC grants reset once (new identity).

## 5. Verification

- `swift build && swift test` (785 tests, `UpdatePolicyTests` among them); `swift build --package-path
  app`; `swift test --package-path app`; `bun test ./app/make-appcast.test.ts ./marketing/sync.test.ts`.
- `KLEOTH_NO_INSTALL=1 bash app/make-app.sh release`: Sparkle embedded, every nested piece signed
  "Kleoth Self-Signed", `codesign --verify --deep --strict` passes, `otool -L` shows
  `@rpath/Sparkle.framework/Versions/B/Sparkle` with `@executable_path/../Frameworks`; the smoke test
  (the app with build folders out of reach, so Sparkle loads only from Contents/Frameworks) passes, and
  its General frame shows the Updates section.
- **`bash app/updater-e2e.sh`** (end to end, ~1 min, touches nothing of the installed Kleoth): two
  copies of the dist app under `dev.kleoth.updateprobe`, signed like the real one, an "installed" one at
  build B and an update at B+1 in a DMG; a throwaway EdDSA key; `make-appcast.ts` writes the feed;
  python serves it on 127.0.0.1. `updatecheck` (Sparkle's real updater with a printing user driver,
  loading the copy's Sparkle.framework so the installer that runs is the shipped one): (1) Sparkle orders
  9 < 10; (2) a feed whose signature is for other bytes is refused ("EdDSA signature does not match")
  and the copy is untouched; (3) the update is found, downloaded, extracted, validated and installed
  over the copy, which is then build 10, verifies `--deep --strict` and carries no quarantine flag.
  Sparkle installs at once when the target app is not running, so there is no "ready to install" step to
  stop at. Passed 2026-11-16 on macOS 26.
- `make-appcast.ts` refusals exercised: a key that isn't the app's, a missing key file, a missing DMG,
  a published build above the new one.

## 6. Manual checklist (a real install; needs 0.5.5 published, or a local feed)

1. 0.5.4 → 0.5.5 by hand (DMG or tar), both Macs: it has no updater yet.
2. Launch 0.5.5: no Sparkle prompt about checking automatically; Settings → General → Updates shows
   "0.5.5 (10)" and the toggle on.
3. With a newer release out: within ~3 s of launch, Sparkle's alert in front ("A new version of Kleoth
   is available!"), Kleoth in the Dock while it's up and out of it after.
4. A find later in the day: no alert; the popover shows the notice; Update brings the alert; Install
   Update downloads; Install and Relaunch quits and reopens the new version.
5. Start a meeting, then Install and Relaunch: the window goes, the popover says "installs after the
   meeting recording"; stop: once the transcription (if auto) finishes, Kleoth relaunches updated.
   Same with a screen recording and a hands-free dictation.
6. After the update: no Gatekeeper prompt, Microphone / System Audio / Accessibility / Screen Recording
   grants intact, dictation pastes.
7. "Check for Updates…" from the popover, Settings and the app menu; "You're up to date" when it is.
8. Toggle off → no check the next day (`defaults read dev.kleoth.app SULastCheckTime` unchanged).
9. `-KleothSimulateFirstRun YES`: no update alert over the welcome window.
10. The second Mac (macOS 27.2, `shck@192.168.0.81`) the same, from 0.5.5 to the next release.

## 7. Error cases

| Case | What happens |
|---|---|
| No network / GitHub down | the scheduled check fails silently and retries next day; a check the user asked for shows Sparkle's error |
| A release without `appcast.xml` | latest/download 404: as above, for every install, until a release carries one (the gate prevents it) |
| A DMG rebuilt after the feed | Sparkle refuses it ("improperly signed"); the gate catches it before publishing |
| Kleoth run from the DMG or a translocated path | Sparkle refuses to update ("move to Applications") |
| /Applications/Kleoth.app owned by another user | Sparkle asks for an administrator password |
| Busy at Install and Relaunch | held until idle (§2); a second Install while busy is called off |
| Quit with an update downloaded | Sparkle installs it at quit, no relaunch |

## 8. Not in scope / later

- A macOS notification (UNUserNotification) for a background find: it needs a new permission prompt.
  The popover notice and the launch alert stand in for it.
- Delta updates (`generate_appcast`'s deltas need every previous archive), signed feeds
  (`SURequireSignedFeed`), beta channels.
- If GitHub "immutable releases" is turned on, a release's `appcast.xml` can't be fixed after
  publishing: a fix is a new release.
- The positioning: `marketing/README.md` holds back "auto-update" until the Developer ID build. In-app
  updates (asking first) are true from 0.5.5; reword at the 0.5.5 review if wanted.
