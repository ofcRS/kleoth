# Demo mode: the meeting and recordings-viewer GIFs from the app's own windows (design, 2026-09-24)

Part 1 of the README demos shipped: `pillsandbox --film --demo` composes the real pill onto a drawn
stage (`docs/assets/demo-dictation.gif`, `demo-screen.gif`). The pill can be filmed that way
because `KleothPillUI` is a standalone library. The History window, the meeting view and the
recordings viewer cannot: they are internal to the `KleothApp` executable and read three live
controllers through the environment. So the meeting demo has to come from the app itself.

The user chose "both, pill films first" on 2026-09-24. This is part 2: a second Kleoth instance,
started with `-KleothDemo <folder>`, renders its own History window over demo data and captures
that window frame by frame. It never touches the user's real Kleoth, data, Keychain or input.

## 1. What a demo instance must never do

A launch audit (2026-09-24) found these side effects. Each one would hit the user's real
instance or data if a demo instance ran them:

| Where | Side effect | Harm next to the real app |
|---|---|---|
| `RecordingController.init` → `AppConfig` | Keychain reads, a one-time `ai_provider` migration **write**, a legacy-item migration in `Keychain.loadLocked` | Keychain writes; an access prompt under another identity |
| `RecordingController.init` | `startWatchingOutputDir` creates `outputDir`; `prewarmTranscriptionModel` → WhisperKit background download (session keyed to `dev.kleoth.app`) | writes; network; a background session shared with the real app |
| `RecordingController.init` | `refreshProviderStatus` → spawns `claude`/`codex` and probes the local server | processes, network |
| `AppDelegate.applicationDidFinishLaunching` | global hotkey; `DictationController.startIfEnabled`; `ScreenRecordingController.startIfNeeded`; `didBecomeActive` observer | see the next two rows |
| `startIfEnabled` | `sweepOrphanedAudio` **moves `<outputDir>/dictations/audio` files to the Trash**; installs the fn+shift monitors; shows the pill | data loss; a second pill and monitor |
| `startIfNeeded` | `sweepInterruptedRecordings` **renames any `*.recording.mp4`** (the real instance's live recording); empties `$TMPDIR/kleoth-recordings` | corrupts a recording in flight |
| `HistoryView.onAppear` → `AppActivation.windowOpened` | switches to a Dock app and `activate(ignoringOtherApps:)` | steals focus |
| `MenuBarExtra`; SwiftUI `Window` scenes | a second menu-bar icon; window frames saved to `dev.kleoth.app` defaults | clutter; the user's saved state changes |
| `DictationController.syncLogStore`, `ScreenRecordingController.recordingsDirectory()` | re-read `AppConfig.settings()` on every load | the lists silently rebind to the real `~/Kleoth` |

## 2. Design

**Two layers, so one missed gate is not enough to do harm.**

1. **A separate identity.** `make-app-demos.sh` assembles a temporary `KleothDemo.app` from
   the debug build (never `make-app.sh`, which installs over `/Applications/Kleoth.app`). The copy
   gets `CFBundleIdentifier = dev.kleoth.demo`, no `CFBundleURLTypes`, no mic/system-audio/
   calendar usage strings (a missed gate that reached for one crashes the copy rather than
   prompting) and an ad-hoc signature without entitlements. It is launched with
   `open -n -W … --args -KleothDemo <folder>`, so launchd, not the terminal, is the responsible
   process. With its own defaults domain, saved state, URL routing, hotkey bindings and TCC
   record, the copy holds none of the user's grants (mic, screen, Accessibility), so even a
   missed gate fails closed. The script unregisters it from LaunchServices and deletes its
   defaults and saved state afterwards. `DemoDirector` refuses to run under `dev.kleoth.app`.
2. **One gate in code: `DemoMode`** (new, `app/Sources/KleothApp/DemoMode.swift`). It reads
   `-KleothDemo <folder>` from the argument domain only, the `-KleothSimulateFirstRun` idiom, so
   nothing persists it. The flag alone switches it on: a bad folder still gets every gate, and
   the director quits. When set:
   - **`Keychain`:** the cache starts from a fixed in-memory seed (consent and onboarding done,
     `output_dir` = the folder, dictation and auto-transcribe off, provider `auto`, no keys) and
     writes stay in memory. The three private functions that make every `SecItem*` call return
     early too. This is the one choke point for every Keychain caller, including both
     migrations, so `RecordingController.init` needs no branch of its own: it reads consent and
     onboarding as done from the seed.
   - **`AppConfig`:** `mergeSettingsFromKeychain` forces `outputDir` to the folder (a temp path
     if the argument is unusable, never `~/Kleoth`) and dictation and auto-transcribe off,
     whatever `config.json` says. `mergeCredentialsFromKeychain` returns no keys, so nothing a
     demo launch runs can spend money or upload. Every controller and list that re-reads
     settings (`syncLogStore`, `recordingsDirectory()`) follows it.
   - **`RecordingController`:** `refreshProviderStatus` and `prewarmTranscriptionModel` return
     at once. `providerStatus` stays nil; the summarized demo meetings never show that button.
   - **`AppDelegate`:** registers no hotkey, skips `startIfEnabled`, `startIfNeeded` and the
     `didBecomeActive` observer, ignores `kleoth://` URLs, and hands off to `DemoDirector`.
   - **`KleothApp`:** `MenuBarExtra(isInserted: .constant(!DemoMode.isOn))`, so the menu-bar
     label never mounts and never opens onboarding or consent.
   - **`AppActivation`:** `windowOpened`/`windowClosed` change no activation policy and never
     activate.

**`DemoDirector`** (new, `app/Sources/KleothApp/DemoDirector.swift`), run by
`-KleothDemoScript meeting|viewer|still` with `-KleothDemoFilm <dir>`:
- Builds its own window (920×600; 1180×800 for the still) with an `NSHostingView` rooted at
  `HistoryView()` and `sceneBridgingOptions = .all` (the toolbar, sidebar toggle and title),
  fed the three controllers through their `shared` instances. `isRestorable = false`, no
  autosave name, light appearance to match the part-1 stage.
- `DemoWindow` keeps the frame it was given (SwiftUI otherwise grows a hosting-view window
  toward its content's ideal size) and answers AppKit's active-appearance selectors with true,
  so it draws as the active window (coloured traffic lights, accent selection) while it is
  never key and the app is never active: a real key window would take the user's keystrokes.
- The window is ordered **behind** every window and never made key. An App Nap activity keeps
  the capture timer at full rate.
- Runs a fixed script through the hooks HistoryView already has: `selectedMeetingID` and
  `HistoryRouting.requestedScope`. Scrolling eases the detail's `NSScrollView` to a section
  found through SwiftUI's own accessibility tree (in-process, no Accessibility grant), with a
  fixed step as the fallback.
- One hook in production views: `RecordingDetailView` observes `DemoMode.playNotification`
  (posted only by the director, and ignored unless `DemoMode.isOn`) to call
  `player.togglePlay()`. Playback is what drives the word highlight.
- Every 1/20 s it captures its own window with `CGWindowListCreateImage(.optionIncludingWindow)`.
  Capturing its own window needs no permission, works while the window is covered, and
  includes the video layer. Off the main thread each frame is set on the part-1 stage (desktop
  gradient, teal glow, window shadow, a caption capsule above the window), deduplicated, and
  written as a PNG with an ffmpeg concat list; then the app quits. A 150 s watchdog quits it
  regardless.
- **Scripts:**
  - `meeting`: the newest meeting (header, TL;DR, summary) → scroll to Action Items → scroll to
    the Transcript → select the second meeting;
  - `viewer`: Recordings, the demo recording selected → play, its words highlighting;
  - `still`: one Retina frame of the newest meeting, no caption.

**Demo data** (`app/branding-src/demo/make-demo-data.ts`, generated fresh into a folder of the
caller's choosing, never committed; it refuses `~/Kleoth`):
- **Meetings:** four fictional English conversations (`app/branding-src/demo/meetings/*.txt`,
  today and yesterday, so the sidebar shows two day groups). Each line is spoken by a macOS
  `say` voice onto its speaker's channel with a quiet room tone under both; `mic.m4a`,
  `system.m4a` and `meeting.m4a` (mic left, system right) follow the recorder's layout.
  `speakers.json` names the other channel, as a rename in the app would.
  - **The transcript and the summary are real:** the repo's own `localtranscribe` probe
    transcribes on device and summarizes with `--provider claude-code` (the default). This
    sends the *fictional* transcripts to the user's own Claude Code account; `--provider local`
    keeps them on the machine if a local server runs. The meeting title is the summary's.
- **Recording:** the part-1 Q4 roadmap slide without the pill (`pillsandbox --slides`, the cursor
  and an outline following the narration) plus a `say` narration, encoded as an H.264 MP4 in
  `screen-recordings/`. `screenrec --sidecar` writes its transcript through the app's own
  on-device recording path (extract, `LocalTranscriber` with word timings, the same record
  fields), plus the title a rename would set.
- No dictation day file: no film shows that tab.
- Every name, company and figure is invented. Nothing is copied from the user's `~/Kleoth`.

**Output:** `docs/assets/demo-meeting.gif` and `demo-viewer.gif`, the same ffmpeg recipe,
captioned "Kleoth's real windows, rendered with demo data". Plus a refreshed
`docs/assets/screenshot-detail.png` from the same data. The current one predates 0.2.0: it shows
the retired `google/gemini-3-flash-preview` chip, the old window chrome, and a few seconds-long test
recordings in the list.

## 3. Verification (before any GIF is committed)

- **Isolation, checked, not assumed.** Before and after a demo run:
  - the real `~/Kleoth` tree listing and mtimes;
  - `defaults read dev.kleoth.app`;
  - the Keychain item's modification date (`security find-generic-password -s dev.kleoth -a settings`);
  - `~/Library/Saved Application State/dev.kleoth.app.savedState`.

  All must be identical. The launch sweeps are checked with canaries in the demo folder
  instead of a live recording of the user's (starting one would record their screen and mic):
  a `*.recording.mp4` the recording sweep would rename and an orphan clip in
  `dictations/audio/` the dictation sweep would trash. Both must be untouched.
- No menu-bar icon and no pill appear, and focus stays where it was. I check this through the
  frontmost-app query before, during and after, never by UI scripting.
- `swift build` for both packages, and `swift test`.
- The normal launch path is unchanged. `DemoMode.isOn` is false without the flag, and every gate
  is an early return behind it. A launch of the regular app still shows the menu bar, the pill
  and the hotkey.

**Result (2026-09-25, `make-app-demos.sh` with the real Kleoth running):** the `~/Kleoth` tree
(1,100 entries with mtimes and sizes), the `dev.kleoth.app` defaults, the Keychain item's
modification date and the saved state were identical before and after; both canaries were
untouched; the frontmost app was the user's browser in all 17 samples across the three films;
`dev.kleoth.demo` left no defaults and no LaunchServices registration. Both packages build and
`swift test` passes. The regular launch was not re-run by hand: relaunching the user's Kleoth
mid-session was not ours to do.

## 4. Not in scope

- Onboarding, Settings and consent windows.
- Live meeting capture. The demo shows files the pipeline already produced.
- The region picker, which stays out of the screen demo.
- A cursor in the app films: the selections are programmatic, and the captions say what happens.

## 5. Risks

- **Production code gains a demo path.** It is contained to argument-gated early returns plus
  one `RecordingDetailView` hook. The `-KleothSimulateFirstRun` flag is the precedent.
- **Owning a `MenuBarExtra`-less launch.** Nothing opens SwiftUI `Window` scenes without the
  menu-bar label. That is why the director builds its own `NSWindow` instead.
- **The first on-device transcription with a newly built probe takes ~4 min** (Core ML
  re-specializes). That's a one-time cost per build.

## 6. Found on the way (app issues, not fixed here)

1. **Recordings' empty state sets a ~900 pt minimum height.** "Select a recording"'s message is a
   `.fixedSize(vertical: true)` Text; measured for the detail column's minimum at near-zero
   width it wraps character by character, so the split view's minimum height is about 900 pt.
   That is likely why the History window can't be made shorter than the screen here, and a
   window that opens on an empty Recordings detail lays its detail title-bar backdrop out for
   that height: a white band ~120 pt down, over the header. The viewer film preloads its
   recording and selection so that pass never happens. The meetings empty state has the same
   Text shape.
2. **On-device meeting transcripts come out as a few long blocks per speaker.** Whisper stretches
   each segment over the silence that follows it, so a channel's segments abut (end = next start)
   and `TranscriptNormalizer` (`maxGap` 1.5 s) never sees a gap to split on: the four demo
   meetings show each speaker's whole side in one or two utterances, with a stray "Thank you."
   hallucinated in the silence. The words and their attribution are right; the turn order is not.
   Likely the same on real meetings. The meeting film shows the summary, action items and
   per-speaker highlights, and no transcript, until it is fixed.
