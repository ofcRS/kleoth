# Demo mode: the meeting and recordings-viewer GIFs from the app's own windows (design, 2026-09-24)

Part 1 of the README demos shipped: `pillsandbox --film --demo` composes the real pill onto a drawn
stage (`docs/assets/demo-dictation.gif`, `demo-screen.gif`). The pill can be filmed that way
because `KleothPillUI` is a standalone library. The History window, the meeting view and the
recordings viewer cannot: they are internal to the `KleothApp` executable and read three live
controllers through the environment. So the meeting demo has to come from the app itself.

The user chose "both, pill films first" on 2026-09-24. This is part 2: a second Kleoth instance,
started with `-KleothDemo <folder>`, renders its own History window over demo data and captures
that window frame by frame. It never touches the user's real Kleoth, data, Keychain or input.

## 1. What a demo instance must never do

A launch audit (2026-09-24) found these side effects. Each one would hit the user's real
instance or data if a demo instance ran them:

| Where | Side effect | Harm next to the real app |
|---|---|---|
| `RecordingController.init` → `AppConfig` | Keychain reads, a one-time `ai_provider` migration **write**, a legacy-item migration in `Keychain.loadLocked` | Keychain writes; an access prompt under another identity |
| `RecordingController.init` | `startWatchingOutputDir` creates `outputDir`; `prewarmTranscriptionModel` → WhisperKit background download (session keyed to `dev.kleoth.app`) | writes; network; a background session shared with the real app |
| `RecordingController.init` | `refreshProviderStatus` → spawns `claude`/`codex` and probes the local server | processes, network |
| `AppDelegate.applicationDidFinishLaunching` | global hotkey; `DictationController.startIfEnabled`; `ScreenRecordingController.startIfNeeded`; `didBecomeActive` observer | see the next two rows |
| `startIfEnabled` | `sweepOrphanedAudio` **moves `<outputDir>/dictations/audio` files to the Trash**; installs the fn+shift monitors; shows the pill | data loss; a second pill and monitor |
| `startIfNeeded` | `sweepInterruptedRecordings` **renames any `*.recording.mp4`** (the real instance's live recording); empties `$TMPDIR/kleoth-recordings` | corrupts a recording in flight |
| `HistoryView.onAppear` → `AppActivation.windowOpened` | switches to a Dock app and `activate(ignoringOtherApps:)` | steals focus |
| `MenuBarExtra`; SwiftUI `Window` scenes | a second menu-bar icon; window frames saved to `dev.kleoth.app` defaults | clutter; the user's saved state changes |
| `DictationController.syncLogStore`, `ScreenRecordingController.recordingsDirectory()` | re-read `AppConfig.settings()` on every load | the lists silently rebind to the real `~/Kleoth` |

## 2. Design

**Two layers, so one missed gate is not enough to do harm.**

1. **A separate identity.** `make-demos.sh` copies the built `Kleoth.app` to a temporary
   `KleothDemo.app`. The copy gets `CFBundleIdentifier = dev.kleoth.demo`, no `CFBundleURLTypes`
   and an ad-hoc signature. It then launches it with `open -n … --args -KleothDemo <folder>`. With
   its own defaults domain, saved state, URL routing, hotkey bindings and TCC record, the copy
   holds none of the user's grants (mic, screen, Accessibility), so even a missed gate fails
   closed.
2. **One gate in code: `DemoMode`** (new, `app/Sources/KleothApp/DemoMode.swift`). It reads
   `-KleothDemo <folder>` from the argument domain only, the `-KleothSimulateFirstRun` idiom, so
   nothing persists it. When set:
   - **`Keychain`:** `get` returns nil and `set`/`delete`/`loadLocked` do nothing. This is the
     one choke point for every Keychain caller, including both migrations.
   - **`AppConfig.settings()`:** returns defaults with `outputDir = <folder>`. Every controller
     and list that re-reads settings (`syncLogStore`, `recordingsDirectory()`) follows it.
   - **`RecordingController.init`:**
     - skips the Keychain merges and reads: consent and onboarding count as done, and the user
       name is empty;
     - skips `refreshProviderStatus`, `prewarmTranscriptionModel` and the calendar read;
     - `providerStatus` stays nil. The summarized demo meetings never show that button.
   - **`AppDelegate`:** registers no hotkey, skips `startIfEnabled`, `startIfNeeded` and the
     `didBecomeActive` observer, and hands off to `DemoDirector`.
   - **`KleothApp`:** `MenuBarExtra(isInserted: .constant(!DemoMode.isOn))`.
   - **`AppActivation.windowOpened`:** in demo mode it neither changes the activation policy
     nor activates.

**`DemoDirector`** (new, `app/Sources/KleothApp/DemoDirector.swift`):
- Builds its own `NSWindow` (960×640, `isRestorable = false`, no autosave name) with an
  `NSHostingController` rooted at `HistoryView()`, fed the three controllers through
  `RecordingController.shared`, `DictationController.shared` and `ScreenRecordingController.shared`.
- The window is ordered **behind** the user's windows and never made key.
- Runs a fixed script through the hooks HistoryView already has:
  - `controller.selectedMeetingID`;
  - `screenRecording.recordingsHistoryRequest` + `selectedRecordingID`;
  - `HistoryRouting.requestedScope`.
- Adds one hook, `screenRecording.demoPlayRequest`, a counter `RecordingDetailView` observes to
  call `player.togglePlay()`. Playback is what drives the word highlight.
- Every 1/20 s it captures its own window with `CGWindowListCreateImage(.optionIncludingWindow)`.
  Capturing its own window needs no permission and includes the video layer. A caption is drawn
  on each frame in the part-1 style. The frames and an ffmpeg concat list go to
  `<folder>/../film/`, then the app quits.
- **Script:**
  1. the meeting list, first meeting selected: title, TL;DR, summary;
  2. a second meeting;
  3. Recordings → the demo recording plays with its words highlighted;
  4. quit.

**Demo data** (`app/branding-src/demo/make-demo-data.sh`, generated fresh into a temp folder each
run, never committed):
- **Meetings:** 2–3 fictional English conversations, each spoken by two macOS `say` voices, one
  per channel. `mic.m4a` + `system.m4a` are combined to `meeting.m4a` with ffmpeg in the app's
  layout.
  - **The transcript is real:** the repo's own `localtranscribe` probe, on device.
  - **The summary is real:** `kleoth summarize --provider claude-code`. This sends the
    *fictional* transcript to the user's own Claude Code account. `--provider local` keeps it
    on the machine if Ollama is running.
- **Recording:** the part-1 `demo-screen` stage frames plus a `say` narration, encoded as
  `screen-2026-09-24-101500.mp4`. The sidecar's word timings come from the real on-device
  pipeline (the `screenrec` probe's `--words`).
- **Dictations:** a hand-written day file with 3–4 entries, for a glimpse of that tab.
- Every name, company and figure is invented. Nothing is copied from the user's `~/Kleoth`.

**Output:** `docs/assets/demo-meeting.gif` and `demo-viewer.gif`, the same ffmpeg recipe,
captioned "Kleoth's real windows, rendered with demo data". Plus a refreshed
`docs/assets/screenshot-detail.png` from the same data. The current one predates 0.2.0: it shows
the retired `google/gemini-3-flash-preview` chip, the old window chrome, and a few seconds-long test
recordings in the list.

## 3. Verification (before any GIF is committed)

- **Isolation, checked, not assumed.** Before and after a demo run:
  - the real `~/Kleoth` tree listing and mtimes;
  - `defaults read dev.kleoth.app`;
  - the Keychain item's modification date (`security find-generic-password -s dev.kleoth -a settings`);
  - `~/Library/Saved Application State/dev.kleoth.app.savedState`.

  All must be identical. The run also passes with the real Kleoth open and **recording a
  screen**: its `.recording.mp4` is untouched.
- No menu-bar icon and no pill appear, and focus stays where it was. I check this through the
  frontmost-app query before, during and after, never by UI scripting.
- `swift build` for both packages, and `swift test`.
- The normal launch path is unchanged. `DemoMode.isOn` is false without the flag, and every gate
  is an early return behind it. A launch of the regular app still shows the menu bar, the pill
  and the hotkey.

## 4. Not in scope

- Onboarding, Settings and consent windows.
- Live meeting capture. The demo shows files the pipeline already produced.
- The region picker, which stays out of the screen demo.
- A cursor in the app films: the selections are programmatic, and the captions say what happens.

## 5. Risks

- **Production code gains a demo path.** It is contained to argument-gated early returns plus
  one `RecordingDetailView` hook. The `-KleothSimulateFirstRun` flag is the precedent.
- **Owning a `MenuBarExtra`-less launch.** Nothing opens SwiftUI `Window` scenes without the
  menu-bar label. That is why the director builds its own `NSWindow` instead.
- **The first on-device transcription with a newly built probe takes ~4 min** (Core ML
  re-specializes). That's a one-time cost per build.
